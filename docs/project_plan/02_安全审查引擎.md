# 02 安全审查引擎（reviewer）

## 职责

PreToolUse 触发后的完整决策管线：从工具调用 JSON 到 allow / ask / deny 决策。
安全子 agent（LLM 审查）在本模块内被编排调用。

## 决策管线（顺序固定，先确定性后概率性）

```
stdin JSON
  │
  ├─ ① 总开关检查      settings.enabled = false → 放行（不审查，exit 0 空输出）
  ├─ ② 工具过滤        tool_name ∉ settings.review_tools → 放行（matcher 宽注册的兜底）
  ├─ ③ 危险规则层      本地正则，确定性，不经过 LLM（需求4）
  │     ├─ 命中 action=deny → 直接 deny，reason = 规则描述
  │     ├─ 命中 action=ask  → 直接 ask，reason = 规则描述
  │     └─ 命中 action=allow → 白名单，直接放行（跳过 LLM，省延迟）
  ├─ ④ 缓存层          hash(tool_name + 规范化 tool_input) 命中且未过期 → 复用上次决策
  ├─ ⑤ LLM 审查层      安全子 agent（需求1/2/3）
  │     ├─ decision=allow → allow，reason 简述
  │     └─ decision=ask   → ask，reason = 分析 + 风险点 + 影响范围
  └─ ⑥ 失败兜底        LLM 超时/报错/输出不可解析 → ask（"安全审查不可用，已转人工"）
```

设计原则：

- **单调收窄**：任何一层失败只会让决策更保守（allow 的前提是明确的安全证据）。
- **确定性优先**：用户规则（③）永远先于 LLM（⑤），LLM 输出不可能覆盖用户显式规则。
- **上下文干净**（需求1）：LLM 只收到系统提示词 + 本次工具调用 JSON，
  不接收对话历史——hook 进程天然拿不到，也主动不向 transcript 请求，
  对话内提示注入对本层无效。

## 被审查内容的构造

| 工具 | 审查对象 |
|------|----------|
| Bash | `tool_input.command`（脚本全文，需求2）+ `description`（主 agent 的意图说明） |
| Write | 目标路径 + 文件内容（默认不审查，用户可在 review_tools 中加入） |
| Edit | 目标路径 + 修改摘要 |

构造审查载荷时做长度截断（默认 8000 字符，超出截断并在载荷中注明），
防止超长脚本撑爆 token 或超时。

## LLM 输出契约

安全子 agent 被要求只输出一个 JSON 对象：

```json
{
  "decision": "allow | ask",
  "risk_level": "low | medium | high",
  "analysis": "一句话分析该指令要做什么",
  "risks": ["具体风险点，每条一句话"],
  "scope": "影响范围：涉及哪些文件/目录/系统/网络"
}
```

解析容错策略：

1. 提取响应中第一个平衡的 `{...}` 块（容忍 ```json 围栏、前后杂文）；
2. JSON.parse 成功且 `decision` 合法 → 采纳；
3. 其他情况一律视为解析失败 → 走⑥兜底 ask；
4. LLM 无权返回 deny（拦截是用户规则的特权），返回 deny 按 ask 处理——
   避免 LLM 幻觉把工作流卡死，拦截决策必须来自用户的确定性规则。

## 展示给用户的 reason 拼装（需求3）

`ask` / 规则 `deny` 的 reason 格式（纯文本，客户端审批框直接展示）：

```
[auto-review] <风险级别>: <analysis>
风险点:
- <风险1>
- <风险2>
影响范围: <scope>
```

## 缓存设计

- 位置：`<数据目录>/cache.json`，结构 `{ "<hash>": { "decision": "...", "reason": "...", "expires": <epoch_ms> } }`
- key：`sha256(tool_name + "\n" + JSON.stringify(tool_input 键排序后))`——键排序保证等价输入命中同一缓存
- TTL：默认 3600 秒，可配置；过期条目读取时惰性删除
- 写入时机：仅 LLM 层结论入缓存（规则层结论不缓存——规则是即时的，且规则变更后旧缓存可能失效）
- 上限保护：条目超过 500 条时整表重建（丢弃过期项），避免缓存文件无限增长

## 日志

`<数据目录>/review.log` 追加写，统一格式：

```
[2026-08-29T10:00:00.000Z][INFO][rule] deny Bash: rm -rf / (命中规则: 递归删除根目录)
[2026-08-29T10:00:05.000Z][INFO][llm]  ask Bash: curl ... (risk=high, 3.2s)
[2026-08-29T10:00:06.000Z][WARN][llm]  timeout after 30000ms, fallback ask
```

级别：INFO（正常决策）/ WARN（超时、解析失败、兜底）/ ERROR（配置损坏）。
日志文件超过 512KB 时轮转（重命名为 .old，重新起笔）。

## 失败兜底的不可绕过性

兜底逻辑（⑥）放在所有 try/catch 的最外层主编排函数中：
`reviewer.review()` 任何未被捕获的异常都映射为 ask + WARN 日志，
hook_main 永远能输出合法决策 JSON 或以 exit code 2 结束（阻断），
不存在"异常导致空输出放行"的路径。
